Design Principles

Immutability at source:

Bronze layer is append-only. Source data is never modified. All transformations create new records in downstream layers.

No direct Gold writes:

All edits — human or AI — must pass through the Draft→Review→Approve workflow. Accidental partial updates to the master are architecturally impossible.

Confidence over certainty:

Conflicting values are not discarded. The AI engine scores each competing value; humans review below-threshold cases. All sources are preserved.

Search-first UX:

Elasticsearch handles all user-facing search. BigQuery is never hit by search queries — only by analytical jobs and internal pipelines.

Observable by default:

Every component emits structured logs to Cloud Logging. Metrics flow to Datadog. Traces span the full request path via OpenTelemetry.

Governed from day one:

Data lineage is tracked from feed receipt through every layer to the delivery channel. PII is classified and access-controlled at column level from initial schema design.

Data Ingestion — D6 Platform

D6 is S&P's internal data ingestion and routing platform. It handles the full lifecycle of feed receipt, parsing, normalisation, and delivery to BigQuery landing tables. The Maritime platform does not build its own ingestion infrastructure — it configures D6 via the Feed Registry.

Feed Registry

Every feed is declared in the Feed Registry before it can be ingested. The registry drives connector configuration, schedule, schema mapping, and routing.

-- Feed registry (Cloud Spanner or BigQuery config table)
CREATE TABLE feed_registry (
  feed_id            STRING  NOT NULL,
  feed_name          STRING,
  provider           STRING,
  domain             STRING,        -- vessel|port|company|cargo|compliance
  delivery_method    STRING,        -- sftp|email|api|websocket|manual
  format             STRING,        -- csv|excel|xml|json|binary
  schedule_cron      STRING,
  sftp_host          STRING,
  sftp_path_pattern  STRING,
  api_endpoint       STRING,
  api_auth_type      STRING,
  landing_table      STRING,        -- BigQuery target table
  field_map          JSON,          -- source field → canonical field
  schema_version     STRING,
  is_active          BOOL,
  contact_owner      STRING
);

D6 Pipeline Steps

  1. Protocol Adapter — SFTP poll, email parse, API call, WebSocket subscribe
  2. Format Parser — CSV/Excel/XML/JSON → normalised JSON
  3. Schema Validator — mandatory fields, type coercion, encoding correction
  4. Metadata Envelope — attach feed_id, ingestion_ts, source_file_ref, row_hash (SHA-256)
  5. BigQuery Delivery — append to Bronze partition table
Dead-letter queue captures all parse failures with the raw payload and error context. 3-attempt retry with exponential back-off. Alert triggered when DLQ depth exceeds configured threshold.

Medallion Architecture

All data flows through three immutable quality layers in BigQuery before reaching the Gold master. A separate Draft/Edit layer handles all pending changes.

Bronze Layer — Raw Landing

  • Append-only, immutable — no record is ever updated or deleted
  • Full raw payload stored as JSON column alongside parsed fields
  • SHA-256 row_hash enables idempotent re-ingestion
  • Retained for 7 years (regulatory requirement)
  • Partitioned by record_date, clustered by feed_id
CREATE TABLE bq_bronze.vessel_raw (
  ingestion_id      STRING  NOT NULL,   -- UUID
  feed_id           STRING  NOT NULL,
  source_file_ref   STRING,             -- gs://... URI
  ingestion_ts      TIMESTAMP NOT NULL,
  record_date       DATE,               -- partition column
  raw_payload       JSON,
  row_hash          STRING,             -- SHA-256 dedup key
  processing_status STRING DEFAULT 'PENDING'
)
PARTITION BY record_date
CLUSTER BY feed_id, processing_status;

Parsed, type-checked, deduplicated records with completeness scores and DQ flags. Source attribution is always preserved.

Gold Layer — Curated Master

Business-ready, bi-temporal, geospatially enriched, AI confidence-scored master records. The authoritative source of truth for all delivery channels.

CREATE TABLE bq_gold.vessel_master (
  vessel_id         STRING  NOT NULL,
  imo_number        STRING  NOT NULL,

  -- Bi-Temporal
  valid_from        TIMESTAMP NOT NULL,
  valid_to          TIMESTAMP,          -- NULL = current
  sys_from          TIMESTAMP NOT NULL,
  sys_to            TIMESTAMP,          -- NULL = current version

  vessel_name       STRING,
  vessel_type       STRING,
  flag_code         STRING,
  deadweight        NUMERIC,
  gross_tonnage     NUMERIC,
  owner_id          STRING,
  operator_id       STRING,
  last_known_position  GEOGRAPHY,
  last_known_position_geojson JSON,
  route_geojson     JSON,               -- last voyage as LineString

  -- Quality
  confidence_score  FLOAT64,
  primary_source_id STRING,
  contributing_sources ARRAY<STRING>,

  record_status     STRING DEFAULT 'ACTIVE',
  approved_by       STRING,
  approved_at       TIMESTAMP
)
PARTITION BY DATE(valid_from)
CLUSTER BY imo_number, flag_code, vessel_type;

Geospatial Design

BigQuery GEOGRAPHY type handles all spatial data natively. No separate geospatial database is required.

Use CaseBigQuery FunctionExample
Vessel positionST_GEOGPOINT(lon, lat)Store AIS position as GEOGRAPHY point
Port boundaryST_GEOGFROMGEOJSON()Port polygon from GeoJSON feed
Voyage trackGEOGRAPHY linestringMulti-point AIS trajectory
Proximity searchST_DWITHIN(pos, centre, dist_metres)Vessels within 50km of port
ContainmentST_WITHIN(point, polygon)Vessel inside EEZ or port boundary
Distance calcST_DISTANCE(a, b)Distance between two vessels
API outputST_ASGEOJSON(geog)Serialize GEOGRAPHY to GeoJSON for API
GeoJSON is also stored as a raw JSON column alongside the GEOGRAPHY column. This preserves arbitrary GeoJSON properties (e.g., feature collections with metadata) that the GEOGRAPHY type cannot represent.

Bi-Temporal Design

Every Gold record carries two independent time axes:

Valid Time (World Time)

When the fact was true in the real world. valid_from / valid_to (NULL = still current).

Example: A vessel was flagged Panama from 2018-03-01 until 2022-11-15.

Transaction Time (System Time)

When the record was inserted into this system. sys_from / sys_to (NULL = current version).

Example: We learned about the flag change on 2022-12-01 from a registry feed.

This enables full point-in-time queries: "What did our system believe about this vessel's flag on 2021-06-01?" and "What was actually true about this vessel's flag on 2021-06-01?" — which may differ if a source reported the change late.

Terahelix — Entity Identifier Mapping

Terahelix resolves the many-to-one mapping between external source identifiers and the platform's canonical internal entity IDs.

Resolution Priority (Vessels)

  1. IMO Number — definitively unique, never reassigned. Highest confidence.
  2. MMSI — may be reassigned between vessels; used with temporal bounds.
  3. Call Sign + Flag — reasonably unique in combination.
  4. Vessel Name + Build Year + GT — fuzzy match with configurable similarity threshold.
  5. Manual Override — admin-managed exceptions for edge cases.
CREATE TABLE terahelix.identifier_registry (
  registry_id      STRING  NOT NULL,
  canonical_id     STRING  NOT NULL,  -- internal entity UUID
  entity_type      STRING  NOT NULL,
  identifier_type  STRING  NOT NULL,  -- IMO|MMSI|CALL_SIGN|NAME|EXTERNAL_REF
  identifier_value STRING  NOT NULL,
  source_id        STRING,
  confidence       FLOAT64 DEFAULT 1.0,
  is_primary       BOOL    DEFAULT FALSE,
  valid_from       TIMESTAMP,
  valid_to         TIMESTAMP
);

AI Confidence Engine

The AI engine resolves conflicts when multiple sources provide different values for the same entity field. It outputs a confidence score (0.0–1.0) and either auto-applies to Gold or queues for human review.

Pipeline

Silver records → Source Hierarchy Resolver → Conflict Detector → Confidence Scorer (Vertex AI) → Auto-apply or Review Queue

Scoring Features

FeatureWeightNotes
Source global rankHighFrom source_registry.global_rank
Field-specific source rankHighOverrides global rank per field type
Corroboration countHighNumber of other sources agreeing
Data age (days)MediumPenalises old source values
Provider reliability scoreMediumHistorical accuracy vs ground truth
Conflict countNegativeMore disagreement = lower confidence
Outlier scoreNegativeStatistical distance from field distribution

Auto-Apply Thresholds

FieldThresholdRationale
IMO NumberManual onlyIdentity field — never auto-changed
Vessel Name≥ 0.95Name changes are significant events
Vessel Type≥ 0.90Stable; multi-source corroboration sufficient
Owner / Manager≥ 0.85Changes frequently; well-covered by sources
Class Status≥ 0.88Compliance significance
AIS Position≥ 0.70Real-time; lower threshold acceptable
Human approvals and rejections feed back to the model. Approvals of low-confidence suggestions create positive training signals; rejections of high-confidence ones trigger source reliability downgrade. Model retrains nightly via Vertex AI pipeline.

Notification System

Event Bus Architecture

GCP Pub/Sub is the notification backbone. All platform events (data changes, feed failures, approval requests) are published to notification-events. The Notification Engine consumes events, matches against configured rules, deduplicates, and enqueues delivery jobs.

Audit System

Append-only BigQuery table captures all material events across the platform. SHA-256 record hash provides tamper detection. Retention: 10 years.

CREATE TABLE bq_audit.audit_log (

  event_ts     TIMESTAMP  NOT NULL,
  actor_id     STRING,
  actor_type   STRING,                -- USER|SERVICE|SYSTEM
  actor_ip     STRING,
  entity_type  STRING,
  entity_id    STRING,

  after_state  JSON,

Data Migration & Backfill

Scope

~1 TB of historical maritime data from legacy systems, flat files, and predecessor databases. Priority order: Vessels → Ports → Companies → Cargo → Events.

5-Phase Approach

PhaseActivityDuration
1 — AssessmentSource inventory, field mapping, data quality audit, volume estimate2 weeks
2 — ToolingDataflow Beam templates, YAML field map configs, validation suite, dry-run environment2 weeks
3 — Dry Run10% sample migration, full validation, analyst spot-check, performance test1 week
4 — Full MigrationBronze push → Silver transform → Terahelix resolution → Gold bi-temporal backfill4–6 weeks
5 — ValidationRow count reconciliation, key metric comparison, domain analyst sign-off, legacy decommission1 week
All migration jobs are idempotent (SHA-256 row hash dedup). Source data is never modified. Legacy system runs in parallel until final sign-off. Rollback = re-run migration from Bronze.
