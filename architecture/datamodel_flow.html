Data Flow & Architectural Principles

End-to-end pipeline from raw feed ingestion through the bi-temporal EAV store to the React UI. Six foundational design principles, governance workflow, partitioning strategy, and JS prototype data layer notes.

Six Architectural Principles
1

Bi-Temporal Data Model

Every EAV row carries valid_from/valid_to (real-world time) AND sys_from/sys_to (system/recording time). Enables point-in-time queries for any attribute on any entity at any past moment.

SELECT * FROM registry.attr_at(
  'vessel',
  '9234567',
  'deadweight',
  '2024-06-01'
);
2

Insert-Only EAV Store

attr_value tables are INSERT-only — a RULE prevents UPDATE/DELETE. Corrections create a new row with sys_to set on the superseded row. Ensures a complete audit trail — no data is ever lost.

3

Confidence-Weighted Multi-Source

Each attribute value carries a source_id and confidence score (0–1). When two sources disagree, the conflict is queued in ingest.conflict_queue. The highest-confidence approved value wins in v_current.

4

Schema-Per-Entity Template

Vessel, Port, Company each follow the identical structural template: entity → attr_value (EAV, partitioned) → raw_ingest (bronze, partitioned) → v_current (materialized view). Adding a new entity type is a single template instantiation.

5

Attribute Registry as Single Source of Truth

All attribute definitions live in registry.attribute_def (and attribute_definitions.json in the JS layer). Filter types, column groups, display orders, validation rules — all data-driven. No hardcoded attribute logic in application code.

6

Zero-Downtime View Refresh

Materialized views are refreshed with the CONCURRENT option — queries against v_current continue serving stale data while the refresh runs. After ingest, call registry.refresh_all_current_views().

Data Governance Workflow
1

Ingest

Feed runs create raw_ingest records. QC rules in ingest.qc_rule validate each attribute value. Failed rows go to conflict_queue.

›
2

Review

Conflicts surfaced in ETL Review page. Analysts approve/reject via workflow.edit_draft → workflow.draft_transition. Every decision logged in audit.change_log.

›
3

Publish

Approved values written to attr_value with workflow_state='APPROVED'. View refresh picks up new values. Rejected values remain in audit log with workflow_state='REJECTED'.

JS Prototype Data Layer

The current implementation uses Vite-bundled JSON files as a zero-backend prototype — all data is compiled into the static asset bundle at build time and served without any REST API or database connection. This enables full UI development and stakeholder review without infrastructure dependencies.

The central mapping chain from schema to UI is:

attribute_definitions.json → attributeRegistry.js → filter config + column config + search config

All filter groups, column picker options, and smart-search field enumerations are auto-generated at module initialisation from attributeRegistry.js — no hardcoded UI configuration lists exist.

All 30 JSON files are imported eagerly at module initialisation. There is no lazy-loading or on-demand fetch in the prototype layer. In the production build these will be replaced by REST endpoints backed by vessel.v_current, port.v_current, and company.v_current.

Coordinate convention — mapData.js: Raw AIS position data is stored in GeoJSON order [longitude, latitude] inside the JSON layer. mapData.js transposes to Leaflet order [latitude, longitude] when constructing marker and polyline arrays. All consumers of mapData.js must use the already-transposed values and must not re-swap coordinates.

USCG MOU naming special-case — pscData.js: The United States Coast Guard MOU authority is stored in source JSON as "USCG" but must be displayed in the UI as "US Coast Guard (USCG MOU)" to match the official authority name used in PSC inspection certificates. pscData.js applies a named mapping constant for this transformation; the raw value is preserved in the mou_code field for database joins.
