Schema Documentation · Platform Layer

Platform Schemas

Four supporting schemas that govern the human layer of the platform: workflow (promotion gate, edit drafts & approvals), audit (immutable change log), ui (personas, saved filters, dashboard layouts) and auth (users, roles, RBAC permissions).

4 schemas 13 tables audit insert-only (RULE) personas.json seeded to ui.persona RBAC via auth.permission

workflow Schema Human-in-the-loop approvals & edit drafts

workflow.promotion_request

Purpose: The explicit promotion gate between the vendor layer (*.attr_value) and the master layer (*.master_value). The ETL pipeline creates a PENDING request for every new or changed vendor value that diverges from the current master. Conflict resolution and manual triggers also route through here. No value enters *.master_value without an APPROVED promotion_request (vendor path) or an APPROVED edit_draft (manual/backdated path). The sole exception is sources where registry.source_attr_weight.auto_promote_to_master = TRUE, which allows programmatic approval.

workflow.conflict

Purpose: Human-raised data conflicts (analyst notices inconsistency between sources). Separate from machine-detected ingest.conflict_queue — these are raised manually and require human resolution. When resolved, the chosen value triggers a workflow.promotion_request (trigger_type = CONFLICT_RESOLVED) rather than writing directly to master. Linked to auth.app_user via deferred FKs added after auth schema is created.

workflow.edit_draft

Purpose: Analyst-proposed manual or backdated value changes that require approval. Supports the 4-state approval machine: PENDING → APPROVED/REJECTED or WITHDRAWN. When APPROVED, the pipeline writes the value to *.attr_value (source_type='MANUAL') and directly to *.master_value (entry_type = MANUAL_ENTRY or BACKDATED) — bypassing the promotion_request gate because the human reviewer is the approver.

audit Schema Immutable change log

audit.change_log

Purpose: Every data change across all entities is written here. Immutable by PostgreSQL RULE — UPDATE and DELETE are silently suppressed. Used for regulatory audit trails, change history display in vessel/port/company detail panels, and forensic investigation.
INSERT-ONLY RULES:
CREATE RULE audit_no_update AS ON UPDATE TO audit.change_log DO INSTEAD NOTHING;
CREATE RULE audit_no_delete AS ON DELETE TO audit.change_log DO INSTEAD NOTHING;
ColumnTypeConstraintsDefaultDescription

entity_type / entity_idVARCHAR(30) / TEXTNOT NULL—Entity affected by the change

NULLABLE FK→registry.attribute_def
NULLAttribute changed (NULL for entity-level events)
operationVARCHAR(10)
NOT NULL CHECK
—INSERT | UPDATE | DELETE | APPROVE | REJECT
old_value / new_valueJSONBNULLABLENULLFull value snapshot before/after the change (typed JSONB for queryability)
actor_idINTEGER
NULLABLE FK→auth.app_user
NULLUser who made the change (NULL for automated pipeline changes)
actor_sourceVARCHAR(30)NULLABLENULLSource code for automated changes (e.g. 'AIS_ORBCOMM', 'IHS_SEAWEB')
source_refTEXTNULLABLENULLExternal reference (run_id, S3 path, API call ID)
logged_atTIMESTAMPTZNOT NULLNOW()Immutable timestamp (cannot be changed by RULE)

ui Schema Personas, saved filters, dashboard layouts

ui.persona

Purpose: Stores pre-configured user personas. Seeded from personas.json (Cargo Analyst, Fleet Manager, Port Operator, Compliance Officer, etc.). The persona_key exactly matches the JSON "id" field. attr_sections, vessel_columns and dashboard_cards arrays drive the entire UI layout for each persona type.

Purpose: Role-to-resource action grants. Resource is a logical name (e.g. 'vessel_data', 'psc_records', 'fixtures', 'admin_settings'). Action is READ | WRITE | APPROVE | ADMIN. The API layer checks these before serving or mutating data.
